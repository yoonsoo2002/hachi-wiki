# 검색 개선 평가 (v0.2.0 → v0.3.0)

HW3 Step 4(DevOps)에서 하치위키 검색을 개선하고, 강의 예시의 방식(데이터 100건, 튜닝 30 / 최종 평가 70, 개선 시도 최대 2회, 같은 데이터·지표로 전후 비교)대로 평가했다.

## 데이터

- `search-corpus.json`: 공부 노트 30개. 전공·교양 과목과 이 수업 내용으로 직접 작성했다(공개 데이터가 아님).
- `search-queries.json`: 검색어 100개와 정답 노트. 다섯 유형으로 나눴다.

| 유형 | 예시 | 개수 |
|---|---|---:|
| 정확한 단어 | `은행원 알고리즘` | 25 |
| 띄어쓰기 차이 | `가상메모리` (노트: 가상 메모리) | 20 |
| 떨어진 여러 단어 | `TCP 신뢰성` | 25 |
| 초성 | `ㄱㅊㅅㅌ` (교착 상태) | 15 |
| 영문 대소문자·기호 | `ci/cd`, `p값` (노트: p-값) | 15 |

- 번호 끝자리가 1·4·7인 30개는 **튜닝용**, 나머지 70개는 **최종 평가용**이다. 최종 평가용은 개선 작업 중에 보지 않았다.

## 진행

1. 기준 측정 (v0.2.0, 튜닝 30): Hit@1 40.0%
2. 개선 시도 1회차: 정규화(NFKC·소문자·공백/기호 제거), 여러 단어 AND, 초성 검색, 제목 우선 정렬 → 튜닝 30에서 Hit@1 100%
3. 2회차 시도는 하지 않았다 (최대 2회 중 1회 사용).
4. 최종 평가 (70, 한 번만 실행): 아래 표

## 최종 결과 (평가 질의 70개)

| 지표 | v0.2.0 | v0.3.0 |
|---|---:|---:|
| Hit@1 (첫 결과가 정답) | 38.6% | 100.0% |
| Recall (정답을 찾음) | 38.6% | 100.0% |
| 결과 없음 비율 | 61.4% | 0.0% |
| 정밀도 (결과 중 정답 비율) | 100.0% | 97.1% |
| 질의당 평균 결과 수 | 0.39 | 1.06 |

정밀도가 조금 떨어진 것은 더 느슨하게 찾으면서 관계없는 노트가 함께 나오는 경우가 생겼기 때문이다(예: 짧은 초성). 대신 제목에서 찾은 노트를 앞에 두어 첫 결과는 모두 정답이었다.

## 한계

- 평가 데이터를 개선한 사람이 직접 만들었고, 질의 유형도 이번 개선이 다루는 경우를 포함하도록 골랐다. 그래서 숫자는 "이 유형의 검색이 되게 되었다"는 확인이며, 실제 사용자 검색 전체의 성능을 뜻하지 않는다.
- 오타 교정, 동의어(도커 = Docker)는 다루지 않는다.
